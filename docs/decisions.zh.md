# 设计决策

塑造这个产品的十二个决策,按读者最可能问到的顺序排列。每一条都按同样的结构写:问题、选择、代价、结果。

---

### 1. 先有意图,再有内容,而不是做一个更聪明的信息流

**问题。** 我看过的每一个推荐系统,包括我自己能做出来的,都在优化用户停留,因为数据奖励的就是这个。一个"更好"的信息流,仍然是信息流。

**选择。** 让用户先说明意图(选一个模式,也可以再写一句话),意图以外的内容一律视为不在范围内,而不是排得靠后。一次刷新只给出有限的一批,没有无限下滑。

**代价。** 多了一步操作。看到第一张卡片之前先选模式,这种步骤大多数产品会在 A/B 测试里删掉。也会有用户写出内容库满足不了的意图。

**结果。** 产品有了存在的理由。后面的每个决策(过滤记录、判官、席位规则)都要以"不在范围内"是一种正式结果为前提才说得通。

### 2. 每一次拒绝都记账,并做守恒校验

**问题。** 一个会把东西挡在门外的"守门人",只有能说清挡了什么、为什么挡,才值得信任。

**选择。** 每个阶段的每一次丢弃都写一行记录(视频、阶段、规则、原因)。界面里能看到这份记录。用户可以申诉,申诉通过后变成长期豁免。每次刷新结束时校验:`进入数 == 展示数 + 折叠数 + 记录行数`,代码里断言,验收测试里也断言。

**代价。** 主路径上多一张表,而且每个新增阶段都必须守这条规矩。

**结果。** 卡片数量看起来不对时,守恒校验是第一个要看的东西。有一次性能改动后出卡变少,校验显示两者无关,把排查引向了别处。透明既是产品功能,也是调试工具。

**代码。** [`src/pipeline/orchestrator.py`](../src/pipeline/orchestrator.py) 中的 `conservation_check`。

### 3. 一个进程,一个 SQLite 文件

**问题。** 能承受的复杂度是有限的,该花在哪里?

**选择。** FastAPI,单进程,SQLite 开 WAL 模式,前端由同一个进程提供。不用队列、不用缓存服务、不用第二个数据库。所有 SQL 放在一个模块里;表结构迁移只加不改,可重复执行。

**代价。** 只能纵向扩容。夜间任务和线上服务共用一台机器。有些能力(向量检索、全文检索)只能在 SQLite 里面做,而不是用专门的服务。

**结果。** 几个月的迭代都花在过滤决策上,而不是基础设施上。需要混合检索时,`sqlite-vec` 和 FTS5 在同一个文件里就解决了。

**代码。** [`src/storage/retrieval.py`](../src/storage/retrieval.py) 是存储层中开源的部分;[`src/storage/db.py`](../src/storage/db.py) 是一层门面,背后是未开源的其余部分。

### 4. 所有 LLM 调用集中在一层,每个调用都有纯代码兜底

**问题。** 依赖模型 API 的产品,一定会遇到 API 失败、变慢或行为改变。

**选择。** 所有模型调用都放在一个包里。每个智能体都带一条失败时走的纯代码路径:默认计划、标记为降级的放行结论、按原文兜底、先存原始输入再做结构化。API 层返回带降级标记的结果,从不返回 500。测试为每个智能体都断言了降级路径。

**代价。** 每个智能体的代码大约翻倍,降级路径还需要自己的测试和日志,否则它在运行时你察觉不到。

**结果。** 模型故障和限流从来没有让网站挂掉过。降级率是一项指标,而不是一次事故。

**代码。** [`src/agent/`](../src/agent/),例如 [`src/agent/judges.py`](../src/agent/judges.py) 中的 `_degrade_quality` / `_degrade_fit`,以及 [`src/agent/discovery.py`](../src/agent/discovery.py) 中的 `fallback_queries` / `fallback_rank`。

### 5. 在判官前面加一道纯代码的成本闸门

**问题。** 对每个候选都跑一次模型,既慢又贵,而大多数候选并不需要。

**选择。** 分流阶段(S4)用免费信号和两个 7 天缓存,把候选分成直接通过、已有缓存结论、需要审核三类。只有需要审核的那一类才交给质量判官。模式贴合判官在每一波之前都先查缓存。

**代价。** 两个缓存都要正确失效。模式贴合缓存的键是提示词版本、模型、语言和用户画像文本合起来的指纹,其中任何一项变化都会让缓存失效。

**结果。** 在一次被跟踪的线上刷新中,102 个候选里有 62 个跳过了质量判官,贴合缓存免费回答了一半的贴合判定。

**代码。** [`src/pipeline/triage.py`](../src/pipeline/triage.py) 中的 `triage`;[`src/core/fit_cache.py`](../src/core/fit_cache.py) 中的贴合缓存键 `fingerprint`;缓存读写在 [`src/storage/retrieval.py`](../src/storage/retrieval.py)。

### 6. 分波推送,先画出上一次的结果

**问题。** 一次完整刷新要几十秒。让用户盯着转圈这么久,人就走了。

**选择。** 用 Server-Sent Events,每判完一批推一波。第一波是直接通过和命中缓存的候选,不用等质量判官。在这一切之前,先从本地池里画出上一次会话的最终画面。一条可见的进度条显示当前在跑哪个阶段。

**代价。** 客户端需要一套帧模型(预览帧最终落定为一份权威的最终帧),还要有细致的排序规则,保证早先展示的卡片仍可能被最终排序降位或去掉。

**结果。** 回访时实测首屏 21 毫秒。这条进度条成了产品的标志。

**代码。** [`src/pipeline/orchestrator.py`](../src/pipeline/orchestrator.py) 中的 `run`,以及 [`src/api/sse.py`](../src/api/sse.py) 中的 SSE 桥接。

### 7. 先测量,再并行

**问题。** 完整刷新在真实数据上要 164.9 秒。凭感觉猜时间花在哪,容易,但会猜错。

**选择。** 给每个阶段打上计时点。数据显示两个 LLM 阶段彼此串行,各自的批次之间也串行。做了三处改动:第一波与质量判官同时跑;各批判定并发执行,并设并发上限;按统计分截取第一波,让最先出来的卡片不必等整批。

**代价。** 需要在并发的生产者内部 yield 的异步生成器,为此仔细重写了一遍才写对。

**结果。** 164.9 秒降到 58.3 秒,减少 65%,在同一份数据上验证。

**代码。** [`src/agent/judges.py`](../src/agent/judges.py) 中的 `_llm_semaphore` 和 `judge_quality`;[`src/config.py`](../src/config.py) 中的 `LLM_MAX_CONCURRENCY` 和 `FIRST_WAVE_MAX`。

### 8. 把 API 配额当作产品约束,而不是运维细节

**问题。** YouTube API 有每日配额,搜索接口还有一份单独的、小得多的配额。白天用完,产品就空了。

**选择。** 两本分开的账,每次调用都由适配器记账,规划器在返回计划前先核对两份预算,离线任务只用固定的预留额度。夜间预热的货架、零成本的本地候选库、判定缓存,存在的主要目的都是让每次刷新少花配额。

**代价。** 每个调用 API 的地方都要写记账代码,规划器也必须考虑预算。

**结果。** 真正的瓶颈原来是搜索那一份,而不是表面上的总配额。没有这两本账就发现不了。

**代码。** [`src/sources/youtube.py`](../src/sources/youtube.py) 中的 `QuotaCounter` 和 `execute_plan`;[`src/agent/planner.py`](../src/agent/planner.py) 中的 `validate_plan`;[`src/config.py`](../src/config.py) 中的 `DAILY_QUOTA` 和 `DAILY_SEARCH_CALLS`。账本表本身未开源。

### 9. 在 SQLite 内做混合检索,并做升级前后对比评估

**问题。** 只靠关键词搜索会漏掉相关视频,中英文混合时尤其明显。上一个向量数据库又会违背决策 3。

**选择。** 用 `sqlite-vec` 存一个小型多语言模型生成的向量,用 FTS5 加 `jieba` 预分词做关键词检索,再用倒数排名融合合并,最后按兴趣分段,避免一个占主导的兴趣挤掉其他兴趣。每一部分都有开关。

**代价。** 一个夜间嵌入任务,外加一次性的历史回填。早期发现的一点:FTS 默认分词器会把一整串汉字当成一个词,所以才引入了 `jieba`。

**结果。** 每个环节都先和升级前的基线对比,确认后才保持开启。这次评估还发现夜间任务曾悄悄停了一周,这本身就是关于定时任务监控的一课。

**代码。** [`src/storage/retrieval.py`](../src/storage/retrieval.py) 中的 `hybrid_search` 和 `rerank_video_ids_by_entry_groups`;嵌入入口在 [`src/sources/embeddings.py`](../src/sources/embeddings.py);`E1_ENTRY_ISOLATION` 等开关在 [`src/config.py`](../src/config.py)。

### 10. 不做可见的用户画像面板

**问题。** 个性化需要一个用户模型。把这个模型展示出来("我们觉得你喜欢……"),会让人觉得被监视。

**选择。** 定一条产品红线:不做展示推断画像的面板。个性化由用户按模式、用自己的话写下的条目驱动,用户可以排序、编辑或删除。推断出的状态在内部存在,会影响席位分配,但从不以"这就是你"的形式展示出来。

**代价。** 对"某张卡片为什么出现"的解释变少了,由拒绝记录来弥补,它解释的是东西为什么*没有*出现。

**结果。** 这条红线后来收窄了,但没有取消:用户自己写的条目可见、可编辑,因为是用户写的;推断出的状态仍然不展示。

**代码。** 按画像条目分配席位在 [`src/pipeline/diversity.py`](../src/pipeline/diversity.py),以及 [`src/pipeline/ranker.py`](../src/pipeline/ranker.py) 中的 `_apply_profile_diversity`。

### 11. 按成本分档选模型,以及一次失败的试验

**问题。** 每个调用都用最好的模型,就等于每个调用都用最贵的模型。

**选择。** 判官和规划器默认用小模型,只在测量证明有必要的地方升级;对话类功能用较大的模型,因为那里要的就是多轮上下文。曾在某一天试用一个更便宜的第三方模型,当天就回退了:慢 1.2–1.6 倍,判定质量更低,还多出一类 ID 对不上的错误。

**代价。** 要同步维护两套模型配置。

**结果。** LLM 费用随需要审核的那一类候选增长,而不是随流量增长。

**代码。** [`src/config.py`](../src/config.py) 中的 `LLM_MODEL`、`LLM_MODEL_FALLBACK`、`CHAT_MODEL` 等设置;[`src/agent/judges.py`](../src/agent/judges.py) 中的 `should_escalate`。

### 12. 先砍范围上线,再小批迭代

**问题。** 最初的计划里有第八个阶段:一个全自动的每周反馈闭环。它是学术上最有意思的部分,也是最不可能改变用户看到什么的部分。

**选择。** 不带它上线,改用命令行工具做人工每周复审。核心稳定之后,把节奏改成每天一个小批次,每批都有书面方案、测试和线上核对,而不是大规模的集中攻坚。

**代价。** 纸面上的故事没那么完整。

**结果。** 产品上线了,并且此后一直在持续迭代。小批次节奏在不到四个月里产生了 664 次提交,线上事故以分钟计。
